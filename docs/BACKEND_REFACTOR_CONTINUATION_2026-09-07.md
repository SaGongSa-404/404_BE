# 백엔드 리팩토링 2차 진행 결과

기준: 1차 구현 `eaa0b27` 이후, 동일 브랜치 `refactor/backend-boundaries-20260907`에서 진행했다. 원래 작업 폴더의 기존 코드 변경은 그대로 유지한다.

## 이번에 구현한 범위

| 계획 | 구현 결과 | 보존한 계약 |
|---|---|---|
| 3단계 · 위시 저장 | 변경 SQL 5개를 `WishlistJdbcRepository`로 분리. `WishlistService`는 검증·중복 처리·트랜잭션 조정 | `SAVED` 조건, 소유자 조건, 변경 행 수, 메타데이터와 멱등 키의 원자성 |
| 3단계 · 소셜 조회 경계 | `MypageSocialQueries`를 소셜 소유의 공개 `SocialActivityQueries`로 대체. 마이페이지와 프로필 명령은 목록·건수 계약만 호출 | 목록 DTO·커서·차단 댓글 집계·취소 투표 제외·batch 조회. JPA 엔티티를 마이페이지로 반환하지 않음 |
| 4단계 · 알림 | `NotificationTriggerQueries`는 대상 SQL, `NotificationTriggerPolicy`는 문구·경로·중복 키·월초 시각, worker는 발행 순서 | 조회당 50건, 대상 조건·순서, 24시간/7일/2일/3일, 한국 시각 월초 09시. 기존 publisher의 중복 방지·afterCommit 유지 |
| 4단계 · 접근 정책 | 기존 `UserAccessService`에 `Clock` 주입, 정확한 정지 만료 경계와 예외 차이를 단위 테스트로 고정 | 없는 사용자에 대한 API 접근 검사는 해당 API에 처리를 맡기지만 토큰 발급은 거부. 인증과 도메인별 온보딩 검사를 임의로 통합하지 않음 |
| 5단계 · 의존성 방어 | 컴파일된 프로젝트 타입 순환 검사 추가. 마이페이지 응답 record를 독립시켜 `MypageService ↔ ProfileCommands` 역참조 제거 | `monthlyBudget`, `notificationEnabled` 응답 필드 동일. Java 타입 위치만 변경 |

## 실행·상태 소유권

- 위시 생성은 `WishlistService.create → WishlistJdbcRepository.insertItem → insertMetadata → WishlistQueries`이며 한 트랜잭션이다. 저장소의 `MANDATORY`는 트랜잭션 없이 쓰는 호출을 거부한다. 메타데이터 DB 실패 뒤 같은 멱등 키로 다시 생성할 수 있는지 테스트한다.
- 마이페이지는 `SocialActivityQueries`에서 완성한 응답을 받는다. SQL join과 batch를 서비스별 개별 호출로 바꾸지 않았다. 계정 탈퇴의 삭제 오케스트레이션은 기존 `AccountWithdrawalService`에 남는다.
- 알림의 대상 조회와 메시지 구성은 분리했지만, 대상 조회 시점부터 전송까지 하나의 트랜잭션으로 묶지는 않았다. 동시 worker의 최종 중복 방지는 여전히 `NotificationPublisher`와 DB unique 조건이 담당한다.
- 월초 알림은 정확히 09시에만 실행되는 것이 아니다. 09시 이후 해당 월의 미발행 대상을 뒤늦게 처리할 수 있는 기존 규칙을 보존했다.
- 접근 제한의 만료 판단은 같은 `Clock` 시각을 사용한다. 실제 활성화 상태의 영속화는 기존 호출 트랜잭션이 담당하며, 토큰/OAuth 통합 테스트도 함께 실행한다.

## 계획 대비 조정과 남은 범위

3·4단계의 주요 책임 경계를 구현했다. 모든 도메인에 동일한 포트/어댑터 폴더를 강제하거나 모든 오류를 하나의 예외로 합치지는 않는다. 기존 접근 정책의 차이는 결함으로 단정하지 않고 보존했다. 소셜 내부 게시물·댓글·투표 서비스 전체 재작성과 job submit/get 저장소 추가 분리는 현재 변경에 포함하지 않는다.

5단계는 로컬 회귀·의존성 검사와 제한된 조회 성능 비교를 수행한다. 전체 요청의 p95, 동시 부하·DB 잠금 대기·queue 지연, 실제 외부 수집률·FCM 전달, 원격 CI·리뷰·배포 후 검증은 아직 별도 작업이다. 따라서 전체 리팩토링 및 운영 수용 완료를 선언하지 않는다.

## 검사 해석

`BackendDependencyCycleTest`는 JDK의 `jdeps`로 컴파일된 프로젝트 타입을 읽어 내부 클래스를 외부 클래스에 합친 그래프에서 순환을 찾는다. 소스 import만 세는 검사보다 실제 바이트코드 참조에 가깝지만, 리플렉션·설정 문자열·인라인 상수·운영 연결은 포함하지 않는다. 실행 가능한 빈 사이의 순환만 검사하는 것도 아니다.

`BackendReadBenchmarkTest`는 선택 실행이다. 두 작업 트리에 같은 fixture/측정 코드를 사용하며, 각 경로마다 100회 준비 호출 후 200회 측정하는 작업을 4회 반복한다. HTTP·인증·네트워크 구간을 제외한 Spring 서비스→로컬 PostgreSQL 직렬 호출이다. 쿼리 수는 매 라운드 전체 호출에 대해 검증한다. 단일 개발 머신에서 기준 코드→변경 코드 순서로 실행하므로 환경·JIT·캐시·실행 순서의 영향을 배제하지 못한다.

## 최종 로컬 검증

- `./gradlew test jacocoTestReport bootJar --no-daemon`: 성공. 테스트 715개, 실패 0, 오류 0, 건너뜀 10개(기존 9개와 선택 실행 벤치마크 1개). 벤치마크는 양쪽 작업 트리에서 별도로 실행해 성공했다.
- 컴파일 타입 그래프: 타입 289개, 참조 745개, 순환 0개. 1차 구현에 있던 응답 DTO 역참조도 이번에 제거했다.
- 실제 DB 제약 위반을 이용한 위시 메타데이터 실패 테스트에서 항목·멱등 키 롤백과 재시도를 검증했다. 임시 제약은 `finally`에서 제거한다.
- 마이페이지 조회당 prepared statement 수는 내 게시물 5회, 투표한 게시물 4회로 유지됐다.
- `docs/understanding.html`: Chromium에서 탐색·검색·흐름·영향 범위·퀴즈·테마·모바일 화면과 링크를 확인했다. 퀴즈는 10개이며 JavaScript 오류는 없었다.
- 원격 CI, push, PR, 배포는 수행하지 않았다.
