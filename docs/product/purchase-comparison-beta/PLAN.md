# 위굴 구매 비교 개선 및 정식 업데이트 계획

추적: [GitHub #263](https://github.com/SaGongSa-404/404_BE/issues/263).

작성: 2026-09-08. 상태: 기획·실행 가능한 시제품 준비, 앱 구현 및 출시 전.

## 1. 결정과 가설

위굴의 첫 개선 범위는 **사고 싶은 상품을 빠르게 저장하고, 두 후보를 비교한 뒤 실제 구매 상태를 정리하는 경험**이다. 설문은 선택 기능으로 옮긴다. 커뮤니티 성장과 친구 공유는 첫 업데이트 범위에서 제외하고, 비교 경험의 재사용을 확인한 뒤 추가한다.

사용자 문제: 상품을 옮겨 담고 설문을 작성하는 수고에 비해 판단에 도움이 되는 결과가 약하다. 내부 커뮤니티의 응답도 기대하기 어렵다. 기능 수보다 한 번의 실제 구매 고민을 해결하는 가치를 검증한다.

가설: 여러 쇼핑몰에 흩어진 두 후보를 사진·가격·원본 링크·고민 메모와 함께 비교하면, 쇼핑몰 찜이나 카톡보다 선택 과정을 정리하기 편하다. 이는 검증 전 가설이며 사용자 증가를 보장하지 않는다.

## 3. 첫 업데이트의 사용자 흐름

1. 쇼핑몰 공유 또는 링크 붙여넣기로 상품 저장.
2. 정보 수집 성공 시 사진·제목·가격 자동 표시, 수정은 선택.
3. 수집 실패 시 링크를 보존하고 제목만 입력해서 저장. 카테고리는 ETC 기본값, 가격·사진은 비워둘 수 있다. URL만 저장하는 별도 초안 모델은 이번 범위에서 만들지 않는다.
4. 목록에서 상품 두 개를 선택해 비교 화면을 연다.
5. 사진, 이름, 가격, 가격 차이, 원본 구매 링크, 후보별 고민 메모를 본다. 가격이 없으면 차이를 계산하지 않는다. 자동 추천·합리성 판정은 없다.
6. 각 상품을 `고민 중 / 샀어요 / 안 사요`로 정리한다. 후보 선택은 구매 확정과 다르며 한쪽을 샀다고 다른 쪽을 자동 폐기하지 않는다.
7. 샀어요를 누르면 실제 결제 금액과 구매 날짜를 확인한다. 가격 누락 시 금액 입력을 요구한다. 변경 취소·중복 요청·이전 상태 복귀도 처리한다.
8. 정리한 상품은 기록 탭에서 다시 볼 수 있다. 목록 기본 화면은 고민 중인 상품이다.

메모는 선택이며 빈칸이어도 비교 가능하다. 첫 업데이트 비교 조합은 화면 선택으로 생성하고 별도 비교방·댓글·초대 데이터는 만들지 않는다. 후보별 메모와 구매 상태는 로그인 계정에 보관한다.

## 4. 범위

### 포함
- 설문 없는 저장·구매 상태 변경, 선택형 설문 진입.
- 기존 위시템 두 개 비교, 가격 누락·깨진 이미지·긴 제목 처리.
- 후보별 고민 메모, 원본 링크 열기.
- 실제 구매 금액·일자와 지출/회고 연결.
- 기록 보기·상태 정정·요청 재시도 처리.
- 새 기능 제어와 최소 측정.

### 이후 검토
- 설치·가입 없는 친구 비교 투표와 짧은 의견.
- 회고 기록을 다음 구매 판단에 연결.

### 제외
- 공개 커뮤니티 개편, AI 추천, 가격 추적·최저가 탐색, 자동 결제 감지.
- 새 분석 서비스·상시 별도 서버 구축, 기존 데이터 일괄 재분류.
- 앱 전체 디자인 교체와 회원가입/온보딩 전면 개편.

## 5. API·데이터 설계 원칙과 구현 순서

이 절은 구현 계약 초안이며 현재 제공되는 API를 의미하지 않는다.

### 호환성 원칙
- 기존 앱의 v1 결정 API와 네 답변 검증은 보존한다. 모든 사용자의 selfCheckAnswers를 한꺼번에 optional로 변경하지 않는다.
- 새 구매 상태는 별도 API/모델로 도입한다. 기존 GO 기록을 실제 결제라고 소급 확정하지 않고 기존 결정 기록으로 표시한다.
- 설문 생략을 네 개의 false 또는 RATIONAL로 저장하지 않는다. 평가 없음은 평가 없음으로 표현한다.
- purchase_decisions의 rationality_result와 self_check_yes_count는 NOT NULL이며 상호 CHECK 제약이 있다. nullable 변경만으로 끝낼 수 없다. 구현 전 구형 앱 조회·통계·캐릭터 반응까지 계약 테스트로 확인한다.
- 권장 설계는 별도 구매 상태 기록과 선택형 평가의 분리다. 기존 예산 장부와 연결하되 기존 GO에서 이미 반영한 지출의 이중 계산을 막는다.
- 새 상태 기록은 소유자 검증, 멱등성 키, 동시 갱신 충돌 검사를 포함한다. 동일 구매를 두 번 눌러도 지출·회고는 한 번만 반영한다.
- 초기 beta 변경은 추가 테이블/필드 중심으로 작성한다. 기존 레코드는 일괄 변경하지 않는다. 확정 DB 설계는 구현 PR에 migration·구형 조회 결과와 함께 명시한다.

### 작업 단위와 완료 조건

| 순서 | 작업 | 완료 증거 |
| --- | --- | --- |
| P0 | 기획·클릭 시제품 | 저장→두 후보 비교→샀어요→금액 확인→정정 흐름 검토 |
| P1 | 실제 Flutter 동선/출시 버전 확인, API 계약 확정 | 현재 AAB 버전·서버 주소 기록, FE/BE 상태 매핑과 호환성 표 |
| P2 | 새 구매 상태·메모 API, 예산·회고 연결 | 소유권/멱등성/상태 정정/과거 GO 중복 차감 방지/구형 앱 회귀 테스트 |
| P3 | Flutter 저장·비교·기록 화면, 새 기능 노출 제어 | Android 실기기 공유·링크·가격 누락·재실행·정정 검증 |
| P4 | 내부 테스트 | 신규 설치/기존 앱 업데이트/로그인/기존 기록/핵심 쓰기 확인 |
| P5 | 작은 범위 GA 업데이트 | 본인 기기 내부 테스트·기존 앱 호환성·기술 기준 충족 |
| P6 | 출시 후 제품 검증 | 실제 비교 사용과 다음 구매 고민의 재사용 관찰, 기술 검증과 구분 |

P2와 P3의 범위는 P0 화면 검토와 P1 계약 확인 결과를 반영한다. 시제품은 서버에 연결되지 않으며, 앱 구현 완료 증거로 사용하지 않는다.

## 6. 성공 기준과 테스트 진행

확정 조건: 외부 테스트 참여자 확보 불가. FE 저장소는 SaGongSa-404/404_FE가 맞으며 사용자가 배포를 인수한다. 현재 Play 버전은 미확인이다.

- 본인 기기에서 실제 쇼핑 후보 두 개로 저장→비교→구매 기록→정정을 수행한다. 이는 사용성과 기술 검증이며 외부 수요 검증은 아니다.
- 참여자 모집이나 비공개 베타를 GA 선행 조건으로 두지 않는다. 기술 기준을 충족한 작은 범위를 정식 업데이트하고 제품 가치는 출시 후 관찰한다.
- 최소 측정: item_save_attempt/result, comparison_opened, comparison_completed(두 후보 로드 및 화면 노출 성공), purchase_outcome_saved. 이벤트 중복은 eventId로 제거한다. appVersion/익명화된 사용자 키로 구분하며 메모·상품 URL·본문은 분석 이벤트에 담지 않는다.
- 분석 도구는 현재 도입 여부를 확인한 뒤 기존 것을 재사용한다. 별도 유료 분석 시스템은 도입하지 않는다. 서버 요청만으로 화면 노출·재사용 의도를 추정하지 않는다.
- 출시 후 저장 성공, 비교 진입/완료, 구매 상태 정리, 다음 쇼핑 시점의 재사용을 관찰한다. 실제 사용량이 없다면 제품 효과는 미확인으로 남기고 성공으로 보고하지 않는다.
- 매일 접속을 요구하지 않는다. 다음 구매 고민이 생기지 않은 기간과 기능이 유용하지 않아 재사용하지 않은 경우를 구분한다.

기술적 필수 조건: 데이터 손실·계정 간 노출·지출 중복 반영·구매 상태 오류 미해결 0건. 기존 앱 핵심 동작 회귀 확인. 이는 관찰 및 정해진 테스트 범위 내 기준이며 무결함 보장이 아니다.

## 7. 브랜치와 출시 전략

추천: **짧은 기능 브랜치 → 본인 기기 내부 테스트 → 작은 범위 GA 업데이트 → 출시 후 개선**.

외부 참여자를 확보할 수 없으므로 별도 비공개 베타는 현재 계획에서 제외한다. 베타는 검증할 사람이 있을 때 유용한 배포 수단이며 제품 효과를 보장하지 않는다.

- 현재 문서 작업: docs/purchase-comparison-beta-plan, develop 대상 Draft PR.
- 구현: feat/purchase-outcome, feat/product-comparison 등 작게 분리한 브랜치와 PR. BE와 FE 각각 해당 저장소에서 관리한다.
- 긴 수명의 develop/beta/production 세 갈래를 추가하지 않는다. 필요한 경우 릴리스 안정화 기간에만 release/<version>을 짧게 사용하고 수정은 develop에도 반영한다.
- Git 브랜치는 코드 분리, Git 태그/Release는 빌드 식별, Play 트랙은 앱 배포 대상을 구분한다. 하나가 다른 하나를 대신하지 않는다.
- BE develop 병합은 현재 자동 배포를 유발한다. 앱이 같은 서버를 쓰면 베타 트랙도 서버 변경 영향을 격리하지 못한다. QA 이름이나 8081 standby만으로 별도 베타 환경이라고 간주하지 않는다.
- 기본안은 기존 서버에 하위 호환 API를 추가하고 새 기능은 기본 OFF, 내부 검증 중에는 본인 계정에만 서버에서 쓰기를 허용하고, GA 준비가 끝나면 일반 사용자에게 활성화한다. FE 표시만 숨기거나 클라이언트의 beta=true만 신뢰하지 않는다. 출시 앱의 서버 주소 확인 후 적용한다.
- 호환성·구형 앱 조회 안전을 확보할 수 없으면 해당 변경을 공용 서버에 배포하지 않고 로컬/격리 테스트에서 해결한다. 소규모 프로젝트라는 이유로 데이터 호환성 검증을 생략하지 않는다.

| 단계 | 대상 / 목적 | 다음 단계 조건 |
| --- | --- | --- |
| Internal testing | 본인 기기에서 설치/업데이트 및 핵심 오류 확인 | 실기기 핵심 동작·구형 앱 공존 검증 |
| Production (GA) | 기존 및 신규 일반 사용자, 작은 기능 범위부터 제공 | 검증 AAB의 설정·계약 확인 후 출시, 이후 사용 관찰 |

공개 베타는 초기 피드백 대상이 불명확해지므로 첫 단계로 선택하지 않는다. 이용자가 적으면 GA 1% 같은 비율 배포는 관찰 인원이 거의 없을 수 있다. 내부 테스트 후 정식 업데이트를 기본으로 하고, GA 배포율은 당시 실제 활성 사용자 수로 결정한다.

## 8. 버전·복구·배포 점검

- 기존 Play 앱과 applicationId를 유지한다. 새 앱 등록을 하지 않는다.
- 로컬 FE pubspec의 1.0.0+3은 현재 Play 버전 증거가 아니다. Console 모든 트랙의 사용된 versionCode 최대값을 확인하고 다음 빌드에 더 큰 정수를 쓴다.
- 버전 이름 예시는 다음 minor의 -beta.1이며 실제 값은 Console 확인 후 결정한다. BE/FE 태그는 각각 배포 SHA와 연결한다.
- 배포 기록에는 FE SHA, BE SHA, AAB versionName/versionCode, DB migration, 기능 허용 대상, 테스트 결과, 트랙을 함께 적는다.
- 본인 기기의 실제 설치 버전을 확인한다. 받을 수 있는 버전은 트랙 참여와 versionCode의 영향을 받으므로 정식 버전 전환도 확인한다.
- 기능 차단 시 새 쓰기를 먼저 끄고 기존 기록 읽기·정정 경로는 유지한다. 실험을 종료해도 사용자가 남긴 구매 상태·메모가 사라지면 안 된다.
- Play 배포 중단은 이미 업데이트한 기기를 이전 앱으로 되돌리지 않는다. 필요한 경우 더 높은 versionCode의 수정 빌드를 배포한다.
- DB migration은 되돌리기보다 이전 바이너리와의 호환성 유지 및 후속 수정으로 복구한다. 실제 데이터 변경을 소스 revert만으로 복구된다고 주장하지 않는다.

## 9. 확인된 역할과 남은 정보

- FE 작업 기준: SaGongSa-404/404_FE, 사용자 확인 완료. 코드 작업은 해당 저장소를 기준으로 진행한다.
- Play 배포 담당: 사용자 본인. 기존 담당자가 개발을 중단해 인수 필요.
- 외부 테스트 참여자: 확보 불가. 이를 기다리며 개발·출시를 중단하지 않는다.
- 남은 출시 정보: Play Console 접근 권한, production/테스트 트랙의 versionName/versionCode, 출시 AAB의 서버 주소. 사용자가 지금 버전을 몰라도 코드 작업은 진행 가능하며 업로드 전 확인한다.
- 기존 applicationId를 유지하고 Console 모든 트랙에서 사용된 최대 versionCode보다 큰 다음 값을 지정한다. 로컬 pubspec만으로 정식 배포 버전을 단정하지 않는다.
- 계정 비밀번호·서명 키를 채팅이나 GitHub 문서로 전달할 필요는 없다. Console 접근 권한이 없다면 계정 소유자로부터 초대를 받아 배포를 인수한다.

추가 예산이나 외부 테스트 모집은 현재 계획의 전제 조건이 아니다.

## 공식 배포 근거

2026-09-08 확인. 트랙 구성·테스터 접근과 versionCode는 [Google Play 테스트 안내](https://support.google.com/googleplay/android-developer/answer/9845334?hl=en)를 따른다. 내부 테스트는 최대 100명이며, 이미 출시된 앱의 비공개 테스트 업데이트는 해당 테스트 그룹에 제공된다.

단계 배포 중단의 한계와 재개는 [Google Play 단계적 출시 안내](https://support.google.com/googleplay/android-developer/answer/6346149?hl=en)를 따른다. 이 프로젝트의 내부 테스트 후 GA 경로는 이미 출시된 앱과 외부 참여자를 확보할 수 없는 상황을 고려한 선택이다. Console 계정에 별도 제한이 있는지는 실제 화면에서 확인한다.
