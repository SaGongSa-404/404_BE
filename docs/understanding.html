리팩토링 작업 트리 · 확인됨

갖고 싶은 물건을 수집하고, 고민하고, 결정하고, 돌아보게 만드는 백엔드

위굴 Backend는 쇼핑 링크나 직접 입력으로 SavedItem을 만들고, 예산과 자기 점검을 반영한 구매 결정을 기록하며, 소셜 투표·리마인드·회고까지 이어 주는 Spring Boot API입니다. PostgreSQL이 사용자별 상태의 최종 저장소이고, Google/Kakao OAuth·외부 쇼핑몰·FCM은 시스템 밖 경계입니다.

핵심 축

SavedItem이 수집·결정·소셜·알림을 잇습니다.

상태의 기준

PostgreSQL과 Flyway 스키마가 영속 상태 계약을 소유합니다.

요청 방어

ApiRateLimitFilter가 인증·API·고비용 요청을 IP 단위로 제한합니다.

외부 경계

OAuth 제공자, 쇼핑몰 페이지, Playwright, Firebase FCM에 의존합니다.

이것만은 기억하세요

  1. POST /api/v1/items/import-link도 기본 설정에서는 DB 작업 큐를 거친 뒤 결과를 기다립니다.
  2. 구매 결정은 purchase_decisions 하나만 바꾸지 않습니다. 위시 상태·예산·자기 점검·마스코트·리마인더를 한 트랜잭션 안에서 함께 바꿉니다.
  3. 알림은 먼저 notifications에 중복 방지 키와 함께 저장되고, 커밋 뒤 FCM 전송을 시도합니다.
  4. 외부 요청은 인증보다 먼저 ApiRateLimitFilter를 지나며, 인증·일반 API·쇼핑 import·health 정책이 중첩 적용될 수 있습니다.
  5. 운영 구성은 백엔드 loopback bind와 Caddy·fail2ban·애플리케이션 rate limit의 계층 방어를 전제로 합니다.
  6. 현재 문서는 2026-09-07에 확인한 origin/develop@a4a66e0 기반 리팩토링 작업 트리를 설명합니다. 운영 배포 상태는 별도로 확인해야 합니다.

아키텍처 지도

노드를 누르면 실제 책임·의존성·상태·근거가 오른쪽 맥락 패널에 표시됩니다.

동기 호출 비동기 작업 저장 외부 시스템
이 저장소는 엄격한 단일 아키텍처 패턴으로만 구성되지 않습니다. JPA Repository와 JdbcTemplate SQL이 함께 사용되며, 서비스별로 영속성 접근 방식이 다릅니다.

실행 흐름

실제 코드 경로를 한 단계씩 이동하며 입력, 부수 효과, 다음 단계를 확인하세요.

데이터의 여정

SavedItem이 어떻게 외부 링크에서 구매 결정과 회고까지 이어지는지 보여 줍니다.

1. 수집 ShoppingLinkImportRequest
SHARE 또는 DIRECT_INPUT
2. 검증·변환 URL 공개 호스트 검사, 정규화, HTML 메타데이터 추출
3. 미리보기 ShoppingLinkImportResponse와 WishlistSaveDraft
4. 저장 saved_items와 선택적 item_source_metadata
5. 결정 purchase_decisions, 자기 점검, 예산, 상태 변경
6. 후속 행동 reminder_schedules, notifications, 회고·소셜 피드

대표 입력 모양

ShoppingLinkImportRequest(inputSource, url, title, brandName, price, imageUrl)

DecisionCompleteRequest(itemId, result, finalPrice, rationaleText, selfCheckAnswers)

중요한 의미 변화

SavedItem.status는 SAVED에서 구매 결정에 따라 다른 상태로 바뀝니다.

PurchaseDecision.result 변경 시 예산 차액과 변경 이력도 함께 조정됩니다.

설계 선택

코드와 스키마에서 확인되는 선택과 그 대가입니다.

확인됨

인메모리 fixed-window 요청 제한

선택: 인증 필터보다 앞에서 IP·정책별 window count를 관리합니다.

이유: 외부 저장소 없이 API 폭주와 고비용 import를 빠르게 완화합니다.

트레이드오프: 프로세스 간 상태를 공유하지 않고 재시작 시 초기화되며 capacity 초과 시 fail-open합니다.

바꿀 경우: Caddy 신뢰 경계, 429 계약, load test, Micrometer 지표를 함께 봐야 합니다.

확인됨

동기 API 위에 DB 작업 큐 재사용

선택: ShoppingImportSyncService가 job을 submit하고 polling합니다.

이유: 동일 URL 수집 합치기, 캐시, worker 복구 로직을 한 경로로 모읍니다.

트레이드오프: 동기 요청 스레드가 최대 wait timeout 동안 polling합니다.

바꿀 경우: import API 계약, worker, queue capacity, 클라이언트 재시도 정책을 함께 봐야 합니다.

확인됨

결정 시 여러 상태를 한 트랜잭션에서 갱신

선택: DecisionCommands가 item·budget·self-check·mascot·reminder를 하나의 트랜잭션에서 조정합니다. DecisionService는 HTTP 호환 어댑터입니다.

이유: 사용자에게 보이는 결정 결과와 파생 상태의 원자성을 지킵니다.

트레이드오프: 서비스가 크고 결합도가 높아 변경 영향 범위가 넓습니다.

바꿀 경우: API integration test와 DB 제약·변경 이력을 같이 검증해야 합니다.

확인됨

알림 저장 후 커밋 뒤 푸시

선택: TransactionSynchronization.afterCommit에서 FCM을 호출합니다.

이유: DB에 없는 알림이 기기에 먼저 도착하는 불일치를 줄입니다.

트레이드오프: FCM 실패가 DB 알림을 롤백하지 않으며 별도 재시도 큐는 확인되지 않습니다.

확신 수준: 저장·전송 순서는 확인됨, 실패 재처리 운영 정책은 알 수 없음.

확인됨

JPA와 직접 SQL 혼용

선택: 엔티티/Repository와 JdbcTemplate이 함께 존재합니다.

이유: 복잡한 집계·잠금·조건부 upsert는 SQL로 명시합니다.

트레이드오프: 엔티티 모델만 읽으면 실제 쓰기 경로와 제약을 놓칠 수 있습니다.

바꿀 경우: migration, raw SQL, JPA mapping, schema smoke test를 모두 확인해야 합니다.

위험 지도

증상과 첫 조사 지점을 함께 봐야 실제 디버깅에 쓸 수 있습니다.

높음 · 보안

non-prod trusted header가 사용자 경계를 우회한다

왜 위험한가: prod profile이 빠진 공개 서버에서는 X-User-Id만으로 /api/v1/** 접근이 가능해집니다.

증상: 인증 없는 요청이 사용자 데이터에 접근합니다.

먼저 확인: 활성 profile, SecurityConfig, PublicServerSecurityGuard, 배포 환경변수.

중간 · 설정

reviewer-token은 명시적으로 다시 켤 수 있다

왜 위험한가: 기본값은 꺼졌지만 APP_REVIEWER_TOKEN_ENABLED=true를 주입하면 고정 심사 계정 토큰 발급 경로가 다시 열립니다.

증상: POST /api/auth/reviewer-token이 404가 아니라 토큰 응답 또는 secret 검증 응답을 반환합니다.

먼저 확인: AppAuthProperties, application-prod.yml, 실제 프로세스 환경변수, AppReviewerAuthIntegrationTest.

중간 · 용량 제한

rate limit 추적 키가 가득 차면 새 IP는 fail-open된다

왜 위험한가: maxTrackedKeys에 도달하고 만료 키를 지워도 공간이 없으면 새 key를 제한하지 않고 통과시킵니다.

증상: overflow 경고가 보이면서 일부 새 IP 요청은 제한되지 않습니다.

먼저 확인: ApiRateLimitFilter.logOverflowOnce, APP_API_RATE_LIMIT_MAX_TRACKED_KEYS, 프로세스 메모리.

높음 · 외부 의존성

브라우저 수집은 느리고 직렬화될 수 있다

왜 위험한가: BrowserPageFetcher.fetch 전체가 browserLock 안에 있어 worker concurrency와 실제 브라우저 병렬성이 다릅니다.

증상: queue wait 증가, 동기 import 504, CPU·메모리 급증.

먼저 확인: import Prometheus 지표, 작업 상태, Playwright 로그, fetch timeout.

중간 · 오류 복구

FCM 실패는 영속 알림과 분리되어 있다

왜 위험한가: 커밋 뒤 전송 실패는 notifications를 되돌리지 않고 일반 실패는 로그만 남깁니다.

증상: 앱 안 알림은 있지만 기기 푸시는 오지 않습니다.

먼저 확인: FCM enable 설정, credentials, sender 로그, token 활성 상태.

중간 · 데이터 무결성

결정 변경의 영향 범위가 넓다

왜 위험한가: 결과 변경은 budget delta, item status, reminder, self-check, change log를 함께 바꿉니다.

증상: 통계·홈 예산·회고 대상·리마인더가 서로 맞지 않습니다.

먼저 확인: DecisionCommands.updateResult, transaction rollback, 관련 integration test.

중간 · 숨은 결합

raw SQL과 JPA 모델이 같은 테이블을 공유한다

왜 위험한가: 엔티티 필드 변경만으로는 SQL 문자열과 migration이 자동으로 따라오지 않습니다.

증상: 시작 시 schema validate 실패 또는 특정 API에서 컬럼 오류.

먼저 확인: 전체 rg 검색, Flyway migration, DomainSchemaSmokeTest.

중간 · 분산 상태

rate limit 상태는 프로세스 메모리에만 있다

왜 위험한가: FixedWindowRateLimiter의 각 애플리케이션 인스턴스가 별도 ConcurrentHashMap을 소유합니다.

증상: 재시작 시 제한이 초기화되고 다중 인스턴스에서는 총 허용량이 늘어납니다.

먼저 확인: 실행 인스턴스 수, 재시작 시각, Caddy·fail2ban 상위 제한.

고장 났을 때

증상부터 시작해 가장 짧은 근거 경로로 들어갑니다.

API가 401 또는 403으로 실패한다
  1. /health로 애플리케이션 자체 상태를 분리합니다.
  2. prod/non-prod profile과 SecurityConfig의 경로 규칙을 확인합니다.
  3. JWT의 issuer, token_type=access, 만료를 확인합니다.
  4. CurrentUserIdArgumentResolver와 UserAccessService에서 사용자 상태·onboarding 차단 여부를 확인합니다.
쇼핑 링크 가져오기가 느리거나 504가 난다
  1. shopping_import_jobs에서 job의 status, attempt_count, started_at을 확인합니다.
  2. ShoppingImportJobScheduler.hasClaimableJob와 worker enabled/concurrency를 확인합니다.
  3. 대상 사이트별 Jsoup 응답, fallback 조건, Playwright timeout과 challenge page를 확인합니다.
  4. 동일 crawl_key leader/follower와 cache TTL이 기대대로 작동하는지 확인합니다.
결정 후 예산이나 위시 상태가 맞지 않는다
  1. purchase_decisions와 saved_items.status를 같은 item_id로 비교합니다.
  2. 해당 사용자의 timezone과 budget_cycles.year_month를 확인합니다.
  3. purchase_decision_change_logs에서 결과 변경 여부를 확인합니다.
  4. DecisionApiIntegrationTest와 DecisionServiceUnitTest로 회귀를 좁힙니다.
앱 알림은 보이는데 기기 푸시는 오지 않는다
  1. notifications 행이 있으면 생성 경로는 통과한 것입니다.
  2. APP_PUSH_FCM_ENABLED와 credentials location을 확인합니다.
  3. user_profiles.notification_enabled, user_notification_settings.push_enabled를 확인합니다.
  4. device_push_tokens.is_active와 FCM sender 로그를 확인합니다.
애플리케이션이 prod에서 시작되지 않는다
  1. PublicServerSecurityGuard의 예외 메시지를 먼저 확인합니다.
